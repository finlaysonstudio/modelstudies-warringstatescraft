# CLAUDE.md

> Keep this file and README.md in sync. When changing scope, tools, targets, or conventions, update both documents. CLAUDE.md is the agent-facing source of truth (how to work); README.md is the human-facing source of truth (what this is and how to use it).

## What this is

Warring States Craft: a branching multi-model war game + values instrument + judges' box, targeting the ChinaTalk "Evals for the Situation Room" contest (deadline 2026-09-01). The active plan is `var/plans/20260816_PLAN_SITUATION_ROOM_SUBMISSION.md`.

## Working rules

- Run `npm test` and `npm run typecheck` before declaring a task done; `npm run format` before committing.
- TypeScript, ESM, moduleResolution bundler, no build step for node packages (each exports `./src/index.ts`). The app builds with Vite.
- Throw `@jaypie/errors` classes, never vanilla `Error`.
- All LLM calls go through the injected `LlmClient` seam (`@modelstudies/workflows`); all persistence through the `Store` seam (`FileStore` rooted at git-ignored `var/`, one directory per model). Never import `@jaypie/llm` from browser code.
- Legacy OpenAI subjects (`packages/workflows/src/llm/legacyOpenAiClient.ts`): `gpt-4-0613`, `gpt-4`, and `gpt-3.5-turbo*` predate structured output (the Responses API rejects `json_schema` for them and ignores tools on `gpt-4-0613`), so `createLlmClient` routes an id in `LEGACY_OPENAI_MODELS` to a Chat Completions client that satisfies `format` with a forced function call, sends no temperature (the API default the paper's `create_chat` used), retries 429/5xx with backoff, and stamps usage with the snapshot the response names. The paper's `gpt-4-1106-preview` and `gpt-3.5-turbo-16k` are retired; `gpt-4-0613` (8k window; a dialog-3, 350-word game peaks near 6.9k tokens on the move-two decision call) is the surviving GPT-4 of that generation, and `gpt-3.5-turbo-16k` now aliases to `gpt-3.5-turbo-0125`. That path is not strict mode (`required` is advisory and a missing key is not an API error), so `gpt-3.5-turbo-0125` flattens a two-array schema often enough to be unfieldable; the capability table (`packages/workflows/src/llm/capabilities.ts`: `ElicitationMode` = `schema` | `text`, `TEXT_ELICITATION_MODELS`, `elicitationFor`) routes it to the text path and `gpt-4-0613` stays on the schema (80 clean arms of `study_a82834f2`).
- Text elicitation (`GameOptions.elicit`: `auto` (default, the capability table) | `schema` | `text`; `--elicit <mode>` on `game-run` and `study-run`; `Run.elicit: "text"` recorded when any seat used it, `Study.elicit` carried onto every arm, `LamparthGroup.elicit` on the report row): on a forced-choice turn a `text` model is asked twice in plain text with no `format` (`answersPrompt` withholds the menu and asks the turn's questions; `selectionPrompt` puts the menu and one instruction with the answers on the history), and `parseSelection` matches the reply against the menu. Only the selection call repeats on an invalid selection, so a retry never re-pays for the prose; `validateChoices`, `CHOICE_RETRIES`, `retries`, and `unusable` are unchanged, so the failure vocabulary and the report's exclusion are the ones already on record. The parser is deliberately narrow because single-letter ids collide with English articles (`a` is both "Military Action" and the indefinite article): the last line (or every line of a bracketed list) is read as ids only when it is id-shaped, otherwise only bracketed ids count, and with no id at all the phrases are matched against labels (exact, then a unique prefix; an ambiguous prefix is dropped, not guessed). The memo path is refused: a `text` model on a non-`choice` scenario throws `ConfigurationError` at engine construction, because `memoFormat`'s two arrays have the same exposure and nothing validates them. Two elicitations of one report is a confound, so a paired text-elicited cell of a schema model measures it.
- Dependency direction: `game`/`survey`/`judges` → `workflows`; `lake` depends on nothing but `@jaypie/errors`; `cli`/`app` → all. `app` imports types only from node packages.
- Scenario content is data (`packages/game/src/scenario/`); engine code stays scenario-agnostic. The thirteen period scenarios are chapters of one chronicle (the Seven Courts saga, `var/plans/20260823_Plan_seven_courts_saga.md`): a `ScenarioText` (`scenario/render.ts`) written once per language (`en`, `zh`) against gazetteer keys (`{qin}`, `{river}`, `{Clan}` capitalizes in en) and rendered by `buildChapter(text, { naming, language, pivot })` into a plain `Scenario`. The world module (`packages/game/src/world/`) holds the gazetteer (`GAZETTEER`: every state, body, place, river, pass, with `chronicle` (real names, the default), `masked` (the invented toponyms), and `modern` (the strait only) renderings in both languages), the cast (`CAST`: a durable `character` block per state, undated; it is prepended to a seat's brief when `ScenarioSeat.state` names a member), the chronicle (`CHRONICLE`: per-chapter `remembers` lines per state; `memoryBefore(state, order)` builds the "What your court remembers" block from every earlier chapter), and the vocabulary sheet. Registration order in `scenarios.ts` (`TEXTS`) is chronicle order, strict chronology: 0 `strait-states` (prologue, c. 485, Wu/Yue/Qi, structure frozen as the Lamparth bridge; `taiwan-strait` is its modern-noun twin outside the chronicle), 1 `land-register`, 2 `salt-and-iron`, 3 `heavy-coin`, 4 `famine-granary`, 5 `schools-of-the-hundred`, 6 `royal-domain`, 7 `conscription-rolls`, 8 `borrowed-road`, 9 `corridor-states`, 10 `hostage-prince`, 11 `river-works`, 12 `assassins-map`; then `PLAIN`: `taiwan-strait` and the eight `lamparth-2024-*` cells (one rendering, refuse any option). `getScenario(id, options)` renders and caches; `renderingsOf(id)` is namings × languages. Seat ids are cast keys (`qin`, `zhao`, `qi`, `council`, `mohists`); seat names and chapter titles are rendered from the gazetteer. No real person is named in played text, no year is stated (`Scenario.chapter` carries `order` and `date` for readers), and the anachronism table in the plan §1.3 is enforced by `RETIRED_TERMS` in `__tests__/chapter.ts`. Every chapter's spec calls `expectChapter(text, shape)` (en/zh isomorphism, every placeholder resolved, no modern noun, no retired term, no chronicle name under `masked`, every pivot applies) and every chapter carries `STANDING_PRIORITIES` (`scenario/shared.ts`) verbatim. `Pivot`s (`{ id, note, en: {from, to}, zh: {from, to} }`) name one pivotal phrase that occurs exactly once and substitute it before rendering; `--pivot <id>` stamps `Run.pivot` and is the treatment for "a pivotal phrase read two ways". Engine strings (`strings.ts`, `EngineStrings`, `stringsFor(scenario)`) are a table keyed by language: the `en` table is the original wording byte for byte (the Lamparth specs depend on it), and a `zh` run is judged and narrated in zh by the same table. Translation fidelity is a documented limitation: the two bodies are written, not translated, and `expectChapter` checks shape, not meaning. `Scenario.simulates` (required, `Headline: detail`) names the modern situation for readers, is rendered on the chapter pages and `/craft/play`, and never reaches a model prompt (`materials.spec.ts` checks it for every rendering, and sweeps every period rendering for `MODERN_NOUNS`; `taiwan-strait` and the Lamparth cells are exempt by id). CLI: `--language en|zh`, `--naming chronicle|masked|modern`, `--pivot <id>` on `game-run` and `study-run`; the run and the study record them.
- Lamparth replication (`packages/game/src/scenario/lamparth2024.ts`): the Lamparth et al. 2024 U.S.-China game transcribed verbatim from the MIT repo's `wargame/*.txt` (Appendix A); `buildLamparth(treatment)` builds one of eight cells (`accuracy` × `training` × `posture`; ids `lamparth-2024-<acc70|acc95>-<basic|significant>-<revisionist|statusquo>`, `LAMPARTH_2024` is the repo default acc95/basic/revisionist). It uses three scenario-agnostic engine features: `Scenario.elicitation: "choice"` (seats answer `turn.questions` and select ids from `turn.choices`; `choiceFormat(turn)` constrains the schema enum; the memo carries `answers` and `choices`, `decision` = selected labels, `options` = the menu), `ScenarioSeat.scripted` (the seat plays `turn.script[seat]`, roster records `SCRIPTED_MODEL`, no LLM call, no debrief; the matrix fills it itself and refuses a model on it), and `Scenario.record: "scripted"` (the public record between turns is the injects and scripted moves, no narrator text). Run-level treatments: `GameOptions.dialog` (N rounds of simulated team dialog before each model decision, carried as chat `history` into the decision call; the brief keeps `dialog[]`), `GameOptions.dialogWords` (a target stated in every dialog prompt, `(about N words for this round of dialogue)`; the paper's chunks were about 350 and its measures move with length, so a length-matched run passes 350; the original enforced nothing and the seam has no portable output cap, so this is an instruction, and the report carries the achieved mean per move as `dialogWords`), and `GameOptions.priorities: false` (withholds the priorities block); the run records `dialog`, `dialogWords`, and `priorities`. CLI: `--dialog <n>`, `--dialog-words <n>`, `--no-priorities`. The cells declare `seatPrompt: "bare"`: the seat's system prompt is the brief and the priorities block only, because the engine's `framed` prompt carries `summary` (which for these cells names the paper, the treatment, and move two's outcome), objectives, the ladder, and a closing line; `lamparth2024.spec.ts` asserts none of that reaches the seat. Forced-choice selections are validated (`validateChoices` in `briefs.ts`: empty, duplicated, or whole-menu selections are invalid); `elicitBrief` retries the decision call up to `CHOICE_RETRIES` times with the invalid reply on the history and `choiceRetryPrompt`, records `retries`, and when the last attempt is still invalid records `unusable` (the memo keeps what the model returned). `selectionFor` and the Lamparth report skip unusable briefs; the report counts the dropped games as `excluded` per group rather than coding them as zeros. The cells declare `report: "lamparth"`; `choices.ts` keeps per-turn helpers (`choiceStats`) for ad hoc grouping.
- Studies and reports: a study (`packages/game/src/study.ts`, `Study` in `types.ts`, files in git-ignored `var/studies/`) is scenarios × models × replicates, each arm one root run stamped with `run.study` and `run.replicate`; `planStudy` writes the arms, `extendStudy` grows a study in place (raises `replicates` and/or adds `models`, appending only the missing (scenario, model, replicate) arms as pending after the existing ones; played arms and their runs are untouched; refuses a lower count or a no-op; a default title follows the new shape), `runStudy` plays every arm that is not complete (an arm whose run finished with a failed model brief is an error and is replayed as a fresh run; an active run is resumed), `buildStudyReport` runs the study's reporting definition. Reporting definitions live in `packages/game/src/reports/` (`REPORTS`: `basic` = escalation per turn/peak/final across replicates; `lamparth` = the paper's statistics: action frequency, total causal effect per treatment factor, aggressiveness, actions selected, Table 2 consistency, and subject-minus-reference differences, every interval a seeded percentile bootstrap); `Scenario.report` names a scenario's definition (default `basic`), a study inherits it and refuses mixed scenarios without an explicit `--report`. Adding a definition: implement `ReportDefinition`, register in `reports/index.ts`, extend `ReportId`, mirror the report shape in the app types. The Lamparth report imports `packages/game/src/reference/lamparth-2024.json` (`LAMPARTH_REFERENCE`, a package asset rather than a store model; the MIT repo's human, GPT-4, and GPT-3.5 dialog-3 games as choice flags only; the repo's GPT files reproduce the paper's Table 2 as the joint probabilities p(agg2 ∧ agg1) / p(agg2 ∧ des1), which the report carries as `table2` beside the literal `conditional`). CLI: `study-run --scenarios "lamparth-2024-*" --models SOL,LUNA --replicates 10 --dialog 3` (`--plan-only`, `--resume <id>`, `--concurrency`; `--resume <id> --replicates 10` and `--resume <id> --models X,Y` extend the study before playing), `study-list`, `study-report <id>` (writes `var/reports/<id>.json`). App: `/craft/studies/:id` and `/awry/studies/:id` (the report rendered, then the arm grid with replay links; the page computes nothing).
- Fork modes: `GameOptions.matrix` (seat → candidate models) forks at turn 1 into one child per combination (`branch.lane: "matrix"`, root keeps `run.matrix`, no turns) and children never fork again; without a matrix the root plays to the scenario's decision point and forks n·2 (independent + consensus). `matrixCombinations` is the single source of the product.
- Human play: `GameOptions.human` (a `HumanPlayer`: `decide`, optional `judge` and `narrate`); any seat assigned `HUMAN_MODEL` (in `seats` or in the matrix) routes to the human every turn; `HUMAN_MODEL` on the panel routes a `JudgePrompt` to `judge` and as the `narrator` routes a `NarratePrompt` to `narrate` (the engine refuses either without the handler). Masking helpers live in `mask.ts`. Within a turn, model seats decide first and human seats last; the `HumanPrompt` carries `roster`, `history` (that run's own prior turns) and `table` (the other seats' briefs this turn). Decision-point fork with `human` set adds a blind and an informed focal memo beside the roster. Human prompts are masked: every model id other than `HUMAN_MODEL` reads `MASKED_MODEL` (roster, history briefs, panel) and the `table` is shuffled; the stored run keeps the truth. The play console withholds replay links from a seated human until the session completes. The browser path is `packages/app/server/play.ts` (Node-side, loaded by the Vite plugin through `ssrLoadModule`, sessions in memory, matrix only) behind `/api/play/*`, and the console page (`pages/PlayConsole.tsx`), unrouted in this build: live play is a later registration-gated deliverable. The server module is the one place in `app` that imports node packages at runtime; browser code still imports types only.

- Matrix view (`packages/app/src/pages/MatrixView.tsx`, `/craft/replays/:id/matrix`): every comparison dimension is an `Axis` (`seat` from the roots' unioned `matrix`, `panel` = judges × `PanelMode`, `root` = source matrix root), and filtering, color-by, split, and the branch table all iterate axes. - Sitting durability: every model call in a survey sitting is journaled before its reply is used, in `var/interview/<id>.jsonl` beside the entity (`Journal` seam in `packages/workflows/src/store/journal.ts`: `FileJournal`, `MemoryJournal` for tests, `parseJournal`; a torn last line is reported as `torn`, never read as a shorter event, and the next append starts a fresh line). The event vocabulary is `packages/survey/src/journal.ts` (`start`, `resume`, `turn` (item, rep, order shown, verbatim content, code, usage, ms, `promptSha1`), `probe` (`replay` marks a backfill), `discard` (`--retry` dropped these reps), `fail` (the terminal failure of a call), `checkpoint`, `stop` (`complete` | `error` | `interrupt` | `budget`)); `foldJournal` folds by (item, rep), first write wins, a hole refuses. The entity is a checkpoint written after every item; on resume `loadSitting` folds the journal over it and the journal wins (`materializeResponses`, drift logged). `RunSittingOptions.signal` stops a sitting between calls (an in-flight call lands and is journaled), checkpoints it as `pending` with `statusDetail: "interrupted at <item> rep <n>"`, and writes `stop: interrupt`; the CLI's first SIGINT/SIGTERM aborts, the second exits. `FileStore.update` writes a temp file and renames it. `verifyInterview` (`interview-verify <id> [--rebuild] [--json]`) recomputes every turn's prompt sha1, compares the entity and probes with the fold, and with `--rebuild` rewrites both from the journal (an entity missing from the store is rebuilt from the `start` line). A fielding (`packages/survey/src/fielding.ts`, `var/fielding/<id>.json`) is one `interview-run`: plan, roster, repetitions, and model → interview id, written before the first sitting and settled after; `--resume <fieldingId>` resumes every sitting it opened (a complete one returns as is). Usage stays on the artifact each call produced (`InterviewItemResponse.usage`, `ProbeEntity.usage`, index-aligned with `values`). Retry: `withRetry` (`packages/workflows/src/llm/retry.ts`) is the outer layer `createLlmClient` applies over both the Jaypie path (which retries inside `Llm.operate` already) and the legacy client (its own loop); `classifyRetry` is the one table (Jaypie `category`, then `status`, then network `code`/message; a 429 naming a quota is terminal, and the legacy client marks one `insufficient_quota:`); `retry: false` removes it, `onRetry` reports absorbed attempts (the CLI logs them), `signal` ends a wait. The CLI tees its `Logger` to `var/log/<yyyymmdd>-<hhmmss>-<command>.jsonl` (`createCliLog`; diagnostic, deletable; the journal is the record).
- Survey cost, latency, estimate, cap, and subsets: usage stays on the artifact each survey call produced (`InterviewItemResponse.usage`, `ProbeEntity.usage`, index-aligned with `values`) and so does wall clock (`InterviewItemResponse.ms`, `ProbeEntity.ms`, the milliseconds the sitting timed around the call, retries and backoff inside; the journal's `turn` and `probe` lines have always carried `ms`, and `interview-verify --rebuild` fills the artifacts of a sitting fielded before latency landed on them). Cost: `interviewUsage({ store, entity })` loads the probes; `usageOfInterviews` sums; `groupInterviewUsage` regroups). The totals type and its adders (`UsageTotals`, `emptyTotals`, `addItem`, `addTotals`, `roundUsd`) live in `packages/workflows/src/llm/usage.ts` and `game/cost.ts` re-exports them. `values-scorecard` carries `usage` per model row and a `ScorecardUsage` (`total`, `rows`, `byModel`) on the scorecard; `/craft/survey` renders every values scorecard the `/data/scorecards.json` index lists (the index stamps `kind`: `values` | `ladder`): one summary row per model scoring its battery sitting, cost and latency folded over every sitting of the model, the sittings expandable beneath (battery, crux, arms), module columns labeled from the scorecard's `modules` with a key under the table. `buildValuesScorecard` refuses a plan with no sittings on record (`NotFoundError`; the CLI default plan is `crisis`, so the battery needs `--plan crisis-situated`). `interview-estimate --plan <id> --panel <p> --repetitions <n> [--explain] [--items <spec>]` (`packages/survey/src/estimate.ts`): calls = items × reps × (1 + explain); tokens per call from a prior sitting of that model on any plan when one exists (`measureUsage`, mean input and output per answer and per probe call), else the stated heuristic (prompt characters / 4 in, 24 out for an answer, 220 out for a probe); dollars from `MODEL_PRICES` at estimate time; every figure names its source (`measured` | `heuristic`). `--budget-usd <n>` on `interview-run` is a `SittingBudget` shared by the roster (`createBudget`, `chargeBudget`, `budgetExhausted`, `budgetDetail` in `interview.ts`): every sitting checks the running sum after each call (an answer and its probe are a pair) and stops as `pending` with `statusDetail: "budget exhausted at $x.xx of $y.yy"` and `stop: budget`; a resume charges what the journal (or, without one, the checkpoint) already holds before asking anything; a fielding-id resume inherits the fielding's recorded cap when `--budget-usd` is absent; unpriced calls count at zero and are named in the detail. `--items <spec>` fields a subset (item names, or one name of a subset the plan declares in `Instrument.subsets`; `resolveItems` refuses an unknown name), the sitting records it as `InterviewEntity.items` (and the fielding as `items`, the `start` line as `subset`), and a resume keeps to it; `items` with `--resume` is refused. `interview-list` lists fieldings with their sittings (plan, model, status, reps, answered/declined, cost) then sittings fielded singly; `interview-cost <id>` (`--json`) folds one sitting by role.
- Instrument plans from markdown: `crisis-situated` (88 items, 16 modules, `packages/survey/src/bank/crisisSituated.ts`) is emitted from `var/instruments/crisis-situated.md` by `npx tsx scripts/emit-instrument.ts <markdown> <bank.ts>` (parser `packages/survey/src/bank/markdown.ts`, `parseInstrumentMarkdown`: the `## 2. Protocol` preamble blockquote, `**Stem.**`, `**Probe.**`; modules `### <Letter> · <title> · <n> items` with an optional `Situation…:` paragraph that leads each item's wording before the stem; items `### <id> · <title>` with statements `1.` and `2.` and `construct:` / `design:` / `game:`; the crux list in the `## … Crux` section). Statement 1 is code 1, the construct-positive pole; `topic` is the module letter; `meta` carries `construct`, `module`, `rung` (position in the module), `design`, `game`; `CRISIS_SITUATED_CRUX` is the plan's `crux` subset (`--items crux`). The markdown is the source of truth and is git-ignored, so `crisisSituated.spec.ts` re-parses it where it is checked out and is reported as skipped elsewhere; re-emit after editing it. `itemFormat` sends enum labels through `schemaLabel` (straight double quotes become typographic; OpenAI strict structured outputs refuses `"` inside schema string literals, met on h7) and `toCode` folds both quote forms before matching. The scorecard carries `kind: "values"`, `bankItems`, `modules` (per-topic label and title), and per-row `items` so the app tells the battery from the crux; the ladder scorecard is the next bullet.
- Arms: a treatment arm is data the plan declares (`Instrument.arms: Record<id, ArmDefinition>` in `types.ts`: `title`, `items` (default the whole bank), `preamble` (replaces the instruction), `probe` (replaces the plan's), `append: "majority"` with `appendText` (`{course}` is the course named), `language` (stamped on the sitting), `rendering` (per item `{ wording, options: [s1, s2] }`, codes unchanged)). `crisis-situated` declares five on the crux: `priorities` (the standing block prepended to the preamble), `informed` (one line appended after the courses naming the course a majority chose; the majority is scheduled 6/6 by `balancedOrders` over the two codes, seed `${plan}:${arm}:${item}` (`:from<n>` on a top-up), independent of option order, recorded per turn as `InterviewItemResponse.majority` and `TurnEvent.majority`; the line names the course by its label because the courses are shown unnumbered), `dress-period` (chronicle gazetteer nouns), `dress-modern` (U.S. / PRC / strait nouns), and `zh` (abstract nouns in zh, its own preamble, stem, and probe). The texts live in the markdown's `## 10. Renderings` section (`**Priorities.**`, `**Majority.**`, `**Preamble (zh).**`, `**Stem (zh).**`, `**Probe (zh).**`, then `### <id> · <period|modern|zh>` blocks with an optional `Situation:` line and statements `1.` and `2.`; every crux item must carry every rendering) and are emitted as `meta.renderings` on each rendered item and `CRISIS_SITUATED_ARMS` (plus `_PRIORITIES`, `_MAJORITY`, `_ZH`, `_RENDERINGS`). Engine: `presentItem(item, arm)` is the item as the arm shows it (idempotent); `itemPrompt(instrument, item, { arm, order, majority })` swaps the preamble and rendering and appends the line, so the prompt stays a pure function of (plan, arm, item, order, majority) and replay and `interview-verify` reconstruct it; `armOf(instrument, entity)` resolves `InterviewEntity.arm` (part of the sitting's identity: a resume reads it, `--arm` with `--resume` is refused, `--items` inside an arm must fall within the arm's items, a language arm refuses a conflicting `--language`); the fielding and the `start` line carry `arm`; `values-scorecard` rows carry `arm` and sort by model then arm; `/craft/survey` shows the arm beside the model. CLI: `interview-run --arm <id>`, `interview-estimate --arm <id> | --arms` (every arm after the default, with an all-arms total).
- Ladder scorecard and prediction join (plan §2.4/§2.5): `buildLadderScorecard({ plan, store })` (`packages/survey/src/ladderScorecard.ts`; CLI `ladder-scorecard --plan crisis-situated`; artifact `var/scorecards/ladder-<plan>.json`, `kind: "ladder"`) reads a plan's sittings as ladders: per item the share of code 1 with a Wilson 95% interval and an `accepted` flag (share at or above 0.5); per module the strip in `meta.rung` order with the position interval (hardest accepted, easiest rejected), `inconsistent`, and `censored` (every answered rung unanimous one way); the document's composites (force ceiling mapped to a `gameRung` by `CRISIS_SITUATED_GAME_RUNGS`, covert, mobilization, commitment, hedging, extraction, deception, settlement with t3/t4 reversed); arm deltas and informed-arm conformity on the crux against the battery; dose deltas (p5-p6, e7-e8, d6-d5); refusal rates; cost folded over every sitting of the model. The default arm reads from the full-battery sitting; the crux sitting rides as a replication check, never pooled. The prediction map (document §4) is data in `packages/survey/src/bank/crisisSituatedPredictions.ts` (`CRISIS_SITUATED_PREDICTIONS`: Lamparth rows bind by option id and numeric turn; chapter rows carry authored labels until a chapter study elicits choices; `*` rows are every chapter's T5/T6; the survey spec holds item names to the bank and `packages/cli/src/__tests__/predict.spec.ts` holds Lamparth ids to the menus and chapter ids to the registry). The join lives in the CLI (`packages/cli/src/predict.ts`; `predict --study <id> [--scorecard ladder-crisis-situated] [--no-save]` writes `var/reports/prediction-<study>.json`): per model and choice turn the options whose readings hold under the model's shares, the observed modal option pooled across cells (cells must agree on the menu), hit where the modal option carries a prediction, chance 1/|menu|, the cross-model modal as the consensus baseline, and the declared `gameRung` beside the judge's peak escalation; models absent from the scorecard are reported `noSurvey`, and unjoined map rows are counted, never dropped silently.
- Usage and cost: `LlmOperateResult.usage` (`LlmUsageItem[]`, one per model call) comes back through the seam; the Jaypie client stamps `usd` on each item with `priceUsage` (`packages/workflows/src/llm/pricing.ts`, table = `LLM.COST` over `LOCAL_PRICES` for ids Jaypie lacks, today the Lamparth-era `gpt-3.5-turbo-0125`, `gpt-4-0613`, and `gpt-4o-2024-08-06`; provider rules in `billableTokens`: Anthropic `input` is already uncached and `output` includes thinking, OpenAI-style providers carry cache reads inside `input` and reasoning inside `output`, Google reports reasoning beside output).
